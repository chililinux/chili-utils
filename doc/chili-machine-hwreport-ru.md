# 🌶️ отчёт-о-оборудовании-chili-machine

**chili-machine-hwreport** создаёт **профиль вашей машины**: маленький текстовый файл с информацией о производителе, модели, BIOS, корпусе и железе. Затем он отправляет профиль создателю VoidBR через issue на GitHub.

С этими профилями **chili-fr** может симулировать на виртуальной машине (QEMU) установку VoidBR на реальные компьютеры пользователей: старые ноутбуки, офисные десктопы, машины с наследственным BIOS или UEFI. Так проблемы проявляются еще до того, как дойдут до вас.

- **Автор:** Вилмар Катафеста
- **Лицензия:** MIT
- **Вовлеченные инструменты:**
  - `chili-machine-hwreport`: создает и отправляет профиль. Это то, что запускает пользователь.
  - `chili-fr`: используйте профиль для имитации машины в QEMU (`-M`).
  - `tools/chili-machine-import`: проверяет и импортирует отправленный профиль. Это инструмент обслуживающего лица и не включается в пакет.
- **Совместимость:** любой Linux с `/sys/class/dmi/id`, включая live USB. Нужно только `bash`.

## 🔄 Процесс от начала до конца

```
 sua máquina                         GitHub                         repositório
┌──────────────────────┐   issue   ┌──────────────────┐ importa ┌───────────────────────────┐
│ chili-machine-       │ ────────► │ [perfil-maquina] │ ──────► │ usr/share/chili-fr/       │
│ hwreport             │           │ Fabricante Modelo│         │ machines/<nome>.conf      │
└──────────────────────┘           └──────────────────┘         └─────────────┬─────────────┘
                                                                              │
                                                                              ▼
                                                                 chili-fr -M <nome> voidbr.iso
```

**1. На вашем компьютере: `chili-machine-hwreport`**
Команда считывает идентификационную информацию о компьютере, такую же, как Linux отображает в `/sys/class/dmi/id`: производитель, модель, BIOS, материнская плата и тип корпуса (ноутбук, настольный компьютер…). Она также считывает процессор, количество ядер, память, тип диска (SATA или NVMe) и режим загрузки (UEFI или устаревший BIOS). На основе этого формируется **профиль машины** (`.conf`).

**2. Отправка: issue на GitHub**
Команда открывает (или показывает ссылку и QR-код на) уже заполненный issue `[perfil-maquina]` в репозитории `chililinux/chili-utils`. Просто нажмите **Submit new issue**.

**3. Конференция и импорт**
Поддерживающий проверяет профиль, который проходит автоматическую проверку: реальные производитель и модель, значения в пределах ожидаемого, никаких личных данных и ни одна машина не повторяется. Затем он включается в `usr/share/chili-fr/machines/` с именем вроде `lenovo-ideapad-s145-15iil`. В этот момент issue получает комментарий и закрывается.

**4. Использование: `chili-fr -M`**
Виртуальная машина начинает представляться **как ваша собственная машина**: тот же производитель, модель, BIOS и тип корпуса, процессор того же поколения и тот же тип диска и загрузки.

## 🔒 Конфиденциальность

✅ **Не требуется root.** Команда никогда не читает защищенные поля DMI.
✅ **Серийный номер, UUID и MAC никогда** не считываются и не отправляются.
✅ **Метка актива** появляется только, когда это текст с завода ("No Asset Tag"…). Некоторые ноутбуки там хранят имя владельца.
✅ **Перед отправкой** показывает всё, что будет отправлено, и просит подтверждение.
✅ **Импорт снова отбрасывает** любой серийный номер, UUID или личную метку ресурса, который появляется в задаче.

## 🚀 Для тех, кто отправляет профиль

```bash
chili-machine-hwreport          # gera, salva, copia e pergunta se envia
chili-machine-hwreport -s       # só gera e salva (não envia)
```

| Опция | Описание |
|-------|-----------|
| `-n`, `--name <nome>` | название профиля (по умолчанию: `fabricante-modelo`) |
| `-s`, `--save-only` | только создает локальный файл, не отправляет |
| `-y`, `--yes` | ничего не спрашивает (подтверждает всё) |
| `--nocolor` | вывод без цветов |
| `-V`, `--version` | показывает версию |
| `-h`, `--help` | показывает помощь |

**Где находится профиль:**
- `~/.config/chili-fr/machines/<nome>.conf`, готов к использованию с `chili-fr -M <nome>`. Работая с `sudo` или `doas`, он идет в домашний каталог того, кто вызвал команду.
- В **буфере обмена**, когда есть `wl-copy` (Wayland) или `xclip`/`xsel` (X11).

**Как работает доставка:*
- **С `gh` установленным и выполненным входом:** проблема создается напрямую через терминал.
- **Без `gh`:** команда показывает уже заполненную ссылку на issue и, с установленным `qrencode`, QR-код для отправки через мобильный телефон. Необходимо быть авторизованным на GitHub, так как он не принимает анонимные issue.
- **Нет аккаунта на GitHub?** Вставьте профиль, который уже находится в буфере обмена, в беседу с сопровождающим в Telegram или в электронное письмо. Если предпочитаете, отправьте файл `.conf`.

## 🧰 Для обслуживающего: `tools/chili-machine-import`

```bash
tools/chili-machine-import            # lista as issues [perfil-maquina] em aberto
tools/chili-machine-import -l -a      # lista todas, inclusive as fechadas
tools/chili-machine-import 2          # importa a issue #2
tools/chili-machine-import -s 2       # só gera o .conf da issue #2, para conferir
tools/chili-machine-import -n nome 2  # importa com outro nome de arquivo
```

При импорте он спрашивает перед каждым шагом:

1. Скачай issue, извлеки блок `conf` и **очисти** профиль: убери лишние пробелы, удали неизвестные ключи и избавься от личных данных.
2. **Действительно** с теми же правилами, что и chili-fr: реальный производитель и модель, тип шасси, модель процессора, ядра, память, шина диска, UEFI, дата BIOS и видеоустройство. Также отклоняет управляющие символы и слишком длинные тексты.
3. Сообщает, если машина **уже зарегистрирована** (тот же производитель, модель и версия BIOS).
4. Сохраняется в `usr/share/chili-fr/machines/<nome>.conf` с указанием источника в заголовке (номер выпуска и кто отправил).
5. Сделай **commit и push** в `main`.
6. **Прокомментируй и закрой** задачу.

Нужно, чтобы `gh` был залогинен, и `jq`.

**GitHub Actions:** рабочий процесс `.github/workflows/import-machine-profile.yml` выполняет тот же процесс с `-y`. Пока он запускается только вручную (Actions → *Импортировать профиль машины* → *Запустить workflow*). Если профиль недействителен, он комментирует в issue, что именно неправильно, и не импортирует. Чтобы импортировать автоматически, когда на issue будет поставлен ярлык `aprovado`, раскомментируйте блок `issues:` в workflow.

## 🖥️ Использование профилей в chili-fr

```bash
chili-fr --list-machines                              # lista os perfis disponíveis
chili-fr -M lg-a410 voidbr.iso disco.qcow2            # simula a instalação num LG A410
chili-fr -M asus-x200ma -m 4G voidbr.iso disco.qcow2  # as opções da linha de comando valem mais que o perfil
sudo chili-fr --machine-from-host=minha-maquina       # cria um perfil desta máquina (com sudo: inclui serial/uuid)
```

`chili-fr` ищет профили в `~/.config/chili-fr/machines/` (пользовательские) и в `/usr/share/chili-fr/machines/` (те, что идут с пакетом). Баш-комплит дополняет имена с помощью `chili-fr -M <Tab>`.

Что меняется в ВМ:
- **Идентичность (SMBIOS/DMI):** гостевая система видит производителя, модель, BIOS, плату и **тип корпуса** реальной машины. Тип корпуса указывается в двоичной таблице SMBIOS, потому что QEMU не позволяет задать это поле другим способом.
- **Процессор:** использует модель QEMU того же поколения (`Penryn`, `Nehalem`, `IvyBridge`…), без инструкций, которых не было в реальном CPU. Например, старые Core i3 идут без AES, поэтому программа, требующая более новых инструкций, терпит сбой в виртуальной машине так же, как и на реальном компьютере.
- **Диск и загрузка:** диск подключается как SATA или NVMe, поэтому установщик видит `/dev/sda` или `/dev/nvme0n1`, как на реальной машине. Загрузка осуществляется через UEFI или Legacy BIOS.

## 📄 Формат профиля

Текстовый файл с одной строкой `chave="valor"` для каждого поля. Строки, начинающиеся с `#`, являются комментариями.

| Ключ | Пример | Описание |
|-------|---------|-----------|
| `desc` | `LG Electronics A410-G.BC44P1` | описание, отображаемое в `--list-machines` |
| `vendor`, `product`, `version`, `family`, `sku` | `LG Electronics`, `A410-G.BC44P1` | идентификация системы (SMBIOS тип 1) |
| `board_vendor`, `board_product`, `board_version`, `board_asset` | `Intel Corp.` | материнская плата (SMBIOS тип 2) |
| `bios_vendor`, `bios_version`, `bios_date` | `INSYDE`, `QL7L3F92`, `03/14/2011` | BIOS (тип SMBIOS 0) |
| `chassis_type` | `notebook`, `laptop`, `desktop`, `convertible`, `minipc`, `other` или номер (1–36) | тип шасси |
| `chassis_vendor`, `chassis_version`, `chassis_asset`, `chassis_sku` | `LENOVO` | шасси (SMBIOS тип 3) |
| `cpu` | `Nehalem`, `IvyBridge,-aes`, `host` | модель процессора QEMU |
| `cpu_name` | `Intel(R) Core(TM) i3 CPU M 390 @ 2.67GHz` | имя процессора, видимое гостем |
| `smp` | `4` | ядра |
| `mem` | `4G` | память |
| `video` | `VGA`, `virtio-vga-gl` | видеоустройство |
| `net` | `e1000e` | сетевая карта |
| `disk_bus` | `virtio`, `sata`, `nvme` | шина диска |
| `uefi` | `true`, `false` | UEFI или устаревший BIOS |

Пример (`lg-a410.conf`):

```conf
desc="LG A410-G.BC44P1 (notebook 2011, Core i3 M 390 Arrandale, BIOS legado INSYDE)"
vendor="LG Electronics"
product="A410-G.BC44P1"
version="TBD"
bios_vendor="INSYDE"
bios_version="QL7L3F92"
bios_date="03/14/2011"
chassis_type="other"
cpu="Nehalem"
cpu_name="Intel(R) Core(TM) i3 CPU       M 390  @ 2.67GHz"
smp=4
mem="3G"
disk_bus="sata"
uefi=false
```

## ⚠️ Ограничения

- **Виртуальный аппаратный уровень:** виртуальная машина представляется как физический компьютер, но устройства — это устройства QEMU. Аккумулятор, зарядное устройство и крышка не эмулируются.
- **Пустые поля:** то, что профиль не заполняет, получает значение по умолчанию в QEMU, например `Standard PC (Q35…)`.
- **Очень новые CPU AMD** используют `cpu=host`, потому что модели AMD в QEMU требуют процессор AMD на компьютере, который запускает виртуальную машину.
